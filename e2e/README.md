# Full-stack E2E

This suite exercises a deployed Systemly frontend and backend rather than mocked modules. Run it from the **Full-stack E2E** GitHub Actions workflow after a staging deployment.

## Required workflow inputs

- `frontend_url`: deployed HTTPS frontend origin.
- `backend_url`: deployed HTTPS backend origin.

The workflow rejects localhost and non-HTTPS targets.

## Required secret

- `RESEND_API_KEY`: used only by the E2E runner to find the unique email generated by the test registration and retrieve its actual HTML. The signup test uses Resend's delivered test recipient address so it does not depend on a personal mailbox.

## Optional staging fixture secrets

These enable destructive or cross-tenant checks. Without them, those specific tests are skipped while the browser, OAuth-contract, health and registration-email tests still run.

- `E2E_EXISTING_USER_EMAIL`: existing staging user for password-reset delivery.
- `E2E_OWNER_EMAIL` / `E2E_OWNER_PASSWORD`: owner of staging tenant A.
- `E2E_FOREIGN_STAFF_ID`: a staff UUID belonging to staging tenant B. Tenant A must receive 403/404 when requesting its workspace.
- `E2E_BOOKING_PAYLOAD_JSON`: complete valid public booking body targeting a dedicated future staging slot. The test submits it twice concurrently and requires exactly one success plus one conflict.
- `E2E_PAYMENT_APPOINTMENT_ID`: dedicated completed staging appointment that has not been paid. The test submits collect-payment twice concurrently and requires at most one successful paid transition.

Never point the destructive fixture secrets at customer production data. Use disposable staging businesses and future appointments.

## What this suite proves

- deployed frontend pages render in a real Chromium browser;
- mobile auth/marketing pages do not horizontally overflow;
- backend readiness includes database + embedded email worker;
- Google OAuth advertises the deployed backend callback instead of localhost;
- registration queues an email, Graphile Worker processes it, Resend sends it, and the browser consumes the verification link from the actual sent email;
- password-reset delivery can be verified with an existing staging user;
- tenant resource guards reject a foreign staff ID;
- scheduling locking rejects a simultaneous double booking;
- invoice state transitions reject simultaneous double payment collection.

Google-provider login itself and Gmail/Outlook inbox placement remain final manual production acceptance checks because automating a real Google account login or consumer inbox is brittle and introduces credential risk.
